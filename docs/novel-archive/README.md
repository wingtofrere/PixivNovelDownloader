# 小说归档第一版（0.1）

基于本地上游 39b997df。这是源码开发版，使用上游显式开发模式加载编译后的小说插件；不是上游签名正式发行包。

## 功能范围

- 多个标签按完全匹配搜索，取并集；全局 `excludedTags`，实际标签 NFKC 标准化后忽略大小写精确匹配。
- `novel_id` 跨标签去重；已完成、排队中、重试中的记录不会被第二个标签重置。
- 任意章节发现系列后，按官方升序目录冻结前 N 个位置，默认 10；逐章过滤，不用后面的章节补足。系列不足 N 篇就取实际数量。
- 不跟踪系列更新，也不自动开始第二轮搜索。首次搜索的日期范围和拆分分页一直保存，程序升级不会自动重扫。
- 默认只下载小说封面；正文图片不请求，TXT/EPUB 合订也不引入旧库中的正文图片。封面遵循原下载器 best-effort 处理。
- 单篇保存 EPUB；系列在 `novel-series-{id}/archive/` 生成 TXT、EPUB、metadata.json。原来的普通合订本不会被覆盖。
- 独立后台线程串行运行，默认请求间隔 6～15 秒；恢复后等待网络重试，持久化 429/403 的退避时间。401 或连续三次 403 暂停等待认证。
- 进度写入原应用数据库里的 `novel_archive_state`，正文和已有下载历史复用上游小说表。

## Windows 启动

重新构建需要 JDK 17 和 Node.js；直接运行已构建版本只需要 Java 17。可以使用本项目 `.tools` 中已准备的便携 JDK，无需改系统 Java。

```powershell
.\scripts\build-novel-archive.ps1
.\scripts\start-novel-archive.ps1
```

首次启动脚本只创建禁用状态的示例配置，默认位置为项目同级的：

```text
E:\AI\PixivNovelArchiveData\config\plugins\novel-archive.json
```

编辑目标标签和全局黑名单，设置 `enabled: true`，先保留 `dryRun: true`。示例标签仅为示例，不会自动启动真实下载。

Cookie 可以通过启动进程的环境变量提供：

```powershell
# 在本机私密终端设置，不要提交到 Git 或发到聊天中。
$env:PIXIV_ARCHIVE_COOKIE = '你的 Pixiv Cookie'
.\scripts\start-novel-archive.ps1
```

脚本将应用以 `--no-gui` 启动到后台。需要时用 `-Foreground` 在前台运行。首次无头启动前，脚本会在当前终端调用上游 `--setup` 引导设置管理员账号；完成后再启动后台进程。随后访问 `http://localhost:6999` 登录并确认下载目录。数据目录可通过 `-RuntimeDirectory` 指定，之后每次必须使用同一目录。

默认 JSON 配置为全局配置。未知字段、空标签、非法日期或限速会明确报错。配置变更后停止并重新启动程序。确认 dry-run 的统计与日志符合预期后，将 `dryRun` 改为 `false` 再启动；dry-run 有单独的进度命名空间，不会将预演结果当成真实已下载。

注意：dry-run 仍会发送搜索/小说详情请求，Pixiv 详情响应本身包含正文；程序不会在预演中保存正文、下载图片或生成小说文件。首次验证请只配置一个低结果量标签及较近的 `since`，不要将预演当成无网络操作。

## 管理

管理员登录后可从同源浏览器请求以下接口；全部受既有管理员权限检查保护：

- `GET /api/novel/archive/status`：状态、每标签页码/日期范围、分类统计、网络冷却。
- `POST /api/novel/archive/pause`：当前小步骤结束后暂停，暂停状态保存到数据库。
- `POST /api/novel/archive/resume`：恢复；可用 `X-Pixiv-Cookie` 提供新的 Cookie，仅保存在进程内存。
- `POST /api/novel/archive/retry-failed`：显式重试失败项，不清理下载历史或搜索检查点。

没有 Cookie 时显示 `AUTH_REQUIRED`，不会开始搜索。网络冷却时检查 status 的 `network.state`、`network.due`；`IDLE_OR_WAITING` 不等于全部成功，需结合 `counts` 检查 FAILED / COVERAGE_INCOMPLETE / DIRTY。

日志按 10 MB 轮转，保留 10 份压缩归档。日志不记录请求 Cookie。关闭浏览器不影响后台线程；Windows 睡眠时没有下载，唤醒后继续。启动脚本不会擅自创建开机计划任务；需要重启后自动启动时，可将同一启动脚本和固定运行目录加入你自己的 Windows 任务计划。

## 升级必须保留的内容

**程序与运行数据分离。不要把运行目录当成构建目录清理。**

1. 暂停任务并正常退出程序，确认后台进程已停止。
2. 备份完整 `PixivNovelArchiveData`，以及上游设置中的下载根目录。本启动脚本将数据库放在运行目录的 `data/pixiv_download.db`；备份应包含数据库及仍存在的 WAL/SHM 文件，不能只复制某个 JSON。
3. 更新源码/替换程序，运行构建；不要删除下载根、数据库、config、state、data。
4. 用相同 `-RuntimeDirectory` 和相同下载根启动。任务以标签、novel_id、series_id 为稳定身份，不以版本号或时间戳重新建任务。
5. 查看 status：页码继续、完成数量保留，重试等待时间不会因升级归零。

首次本版新增表由上游 schema 生命周期创建，旧小说表和历史不变。归档数据格式版本当前为 `1`，与程序版本独立；同格式版本迭代不会清空进度，遇到未来未知版本时拒绝启动归档，绝不覆盖数据。以后更改格式必须提供显式迁移、迁移前备份及旧版本 fixture 测试；禁止 DROP/TRUNCATE 归档事实表或更换身份键。

黑名单修改后会重新检查已有归档元数据、重建系列合订；不删除原单篇文件。若全系列被排除，旧归档合订会保留为 `previous-policy-*`，不再充当当前合订。正常停用插件不会删除归档表。回滚到不认识本表的旧上游版本前，应使用对应备份或确认其 schema 兼容性，不能直接保证跨任意版本回滚。

## 限制与验收边界

- 无真实 Pixiv 请求测试；接口形状依据本地两个仓库及模拟响应验证。
- 搜索按日期二分处理分页上限；无法再拆分的单日超过页数上限会标记 `COVERAGE_INCOMPLETE`，不会宣称全部抓完。搜索结果在扫描期间被编辑、删除或改变可见性时仍可能变化；不承诺平台级完整快照。
- 完成历史归档后不会轮询新作品；系列目录也不刷新。新增目标标签可以继续归档并共享原下载记录。
- 这是任务/章节级断点恢复，不是 HTTP 字节 Range 续传。已完成文件跳过，未完成正文请求可能重做。
- Cookie 过期仍需用户更新；以环境变量提供时需让新进程继承同一私密环境。封面失败不阻止正文保存。
- 文件系统必须支持本地原子替换；磁盘满或文件被占用会重试/显示失败，保留旧合订本。
- 实测自动化覆盖数据库事务、重启继承、系列限制、过滤、输出与请求策略；真实 Windows 睡眠/唤醒和账号可达性仍需小规模手工验收。
